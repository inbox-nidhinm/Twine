# Twine: notes for working on it

The app is called **Twine** (first called eMotion; renamed on 27 September 2026, and on 28 September 2026 the user asked for the old name to go everywhere). Everything says Twine: the repo folder `Documents/Claude Code/Twine`, the source folder `Twine/`, `Twine.xcodeproj` and its target and scheme, the bundle id `com.nidhin.twine` (test copy `com.nidhin.twine.selftest`, `build/TwineTest.app`), the pasteboard types, the `TWINE_` environment variables and `~/Documents/Twine Creations`. Projects end in `.twine` (`com.nidhin.twine.project`); the old `.emotion` type is no longer declared or read, as none were left. `App/FormerName.swift` is the only code with the old name: on the first launch as Twine it moves `~/Documents/eMotion Creations` to `Twine Creations` and copies the `com.nidhin.emotion` settings domain across (each only when the old exists and the new does not; never in the test copy). The version history keeps its two entries about the first rename as they were. The GitHub repo is `inbox-nidhinm/Twine`.

The original brief is `docs/brief.md`. The project is now working through a Jitter-style redesign: `docs/redesign.md` (the brief) and `docs/redesign-decisions.md` (answers, which win where they differ). Read both before a milestone. This file is the map and the rules.

## Rules

- **No em dashes anywhere**: UI strings, comments, docs, commit messages.
- No third-party dependencies without asking.
- Every milestone ends with: `./make-app.sh` with no warnings, `./test.sh` passing, the change written into the top build of `Twine/VersionHistory.swift` (see below), a commit, and a push to `inbox-nidhinm/Twine`.
- **Builds are releases, not changes** (30 September 2026, the user's request): `VersionHistory.builds` has about a dozen entries, each with `features`, `fixes` and `misc` lists (shown as Feature updates, Bug fixes and Misc, an empty list left out). Write each change as a line in the top build's list that fits it; start a new build (which raises the version number) only when the user says to cut one. Fold a change that undoes an earlier one in the same build into the final state. `VersionHistory.pushes` counts pushes to GitHub, the first being v0.0.01 and the 100th v0.1.00 (`release`, shown small beside the card's title): raise it by one in every commit you push. The build numbers in these notes ("build 43") are the old numbering, one per change, from before this.
- The user is a designer, not an engineer. Explain in plain terms.
- No help text in the UI. States are shown, not explained. Put explanations in `.help()` tooltips.
- Views never write literals: every colour, size and radius comes from `Theme` (in `Packages/MotionKit/Sources/Theme`). Values come from the "Flip Design System" page of Figma file `2XErpBfGuIGNU0DkL58Ute` (node 171:2055), with a blue accent (#217FD8, #4C9FEF until 2 October 2026) in place of Flip's green.
- **Accessibility presses do not prove clicks work.** They skip hit testing. To test real clicks without touching the user's mouse, post `NSEvent` mouse and key events through `window.sendEvent` from a temporary in-app hook, and log state after each. After each step post an `.applicationDefined` event through `NSApp.postEvent`: events sent straight to a window skip the event loop, so the undo group never closes, the document never counts as edited, and nothing saves. Remove the hook before committing.
- **Posted events do not reliably reach SwiftUI gestures.** `onTapGesture` and `DragGesture` sometimes ignore events sent through `window.sendEvent` for a whole session, while real `Button`s always respond. Make clickable controls real buttons; for drags in SwiftUI views (the curve editor), set the value from the hook and say the drag itself was not exercised.
- **The save panel runs in another process.** A test hook can fill it in (`directoryURL` is ignored once it is up; set `NSNavLastRootDirectory` in the test copy's defaults instead) and close it with `window.endSheet(panel, returnCode: .OK)`; `panel.ok(nil)` throws. Errors are presented as sheets on the window (`presentError(_:modalFor:...)`) so they show in window captures.
- **`hitTest` takes a point in the view's superview's coordinates.** For the window's content view that is the frame view, which runs upward, while the content view runs downward, so `content.hitTest(content.convert(p, from: nil))` mirrors the point top to bottom. Use `ChromelessWindow.viewUnder(_:)`. A test hook that builds its points the same wrong way passes anyway: that is how canvas hover shipped broken over the top of the canvas in Animate.
- **A test copy's documents can become the user's work.** On 28 September 2026 the user kept working in a TwineTest window the kit had opened, and the next run wiped that project copy. `run.sh` now puts each run's copy in the run's own folder, moves an earlier run of the same name to the Bin, and asks TwineTest to quit (so it saves) before forcing it. Before a run, check whether TwineTest is open and whether its projects changed after the last run; if so, ask the user.
- **Never drive the copy of the app the user is using.** For scripted tests make a copy of `build/Twine.app` with its own bundle id (`com.nidhin.twine.selftest`) and point it at a throwaway project in the scratchpad.
- When driving the running app to verify, the user is often working in other apps. Launch with `open -g`, use accessibility presses (`click button N of ...`) rather than synthetic keys or clicks, and never type unless Twine is frontmost. Setting a SwiftUI text field's value through accessibility does not reach its binding.

## Signing

Ad-hoc signed (`CODE_SIGN_IDENTITY = "-"`), no App Sandbox (ffmpeg and any chosen folder need it off), and the Hardened Runtime on in both configurations (4 October 2026, after the security review): nothing outside can inject code into Twine or attach a debugger to it, and it needs no exceptions (the private Core Animation classes, the cursor swap and launching ffmpeg all work under it). Release leaves out Xcode's `get-task-allow` (`CODE_SIGN_INJECT_BASE_ENTITLEMENTS = NO`). Debug builds one program (`ENABLE_DEBUG_DYLIB = NO`): the runtime refuses to load Xcode's separate ad-hoc-signed `Twine.debug.dylib` ("different Team IDs"), so the test copy would not start. The test copy is re-signed with the runtime and `Tools/SelfTest/TwineTest.entitlements` (`get-task-allow` only), so `sample` and `profile.sh` can read it.

## Testing in the app

`Tools/SelfTest/` holds the kit: install the driver with `install-hook.sh`, build the separate test copy with `make-test-app.sh`, drive it with `run.sh PROJECT NAME "steps"`, profile with `profile.sh`, and always `remove-hook.sh` before committing (`Twine/App/SelfTest.swift` is git-ignored as a guard). The driver is compiled only into the test copy: `make-test-app.sh` builds with `TWINE_SELFTEST_BUILD=1`, which `make-app.sh` turns into `-D SELFTEST`, and `SelfTest.swift` is an empty `run` without it; any other `make-app.sh` refuses while the hook is installed (4 October 2026), so remove it before the release rebuild. Its README lists every step and the ways a test can fool you. `make-test-app.sh` runs `make-app.sh`, so it replaces `build/Twine.app`, which the user may have open: say so first, and rebuild release before finishing. Unit tests stay in the packages (`./test.sh`); the kit is for what only the running app shows.

## Decisions worth knowing

Three things hold everywhere:

- **Layers are stored back to front** (last in the array is in front). The layers panel shows them reversed.
- **Coordinates are Figma's**: origin top-left, y down, rotation clockwise in degrees (Figma's own rotation is counter-clockwise: an importer negates it). Anchor is in pixels from the layer's top-left. Scale 1 is 100%, opacity 0 to 1.
- **Actions, not keyframes.** A layer's properties are plain values: its design state. `Project.actions` is a flat list; each `Action` targets one layer, has a start, a duration (0 is instant), an easing, and an `ActionSpec` carrying its own typed optional initial value and end value. Layers have no in or out points.

Everything else is in `docs/decisions/`, one file a topic. **Before working on an area, read its file.** When a decision is made or changed, write it into the right file (and add its name here if it is a new topic), not into this file.

## Performance

Performance is one of the most important parts of the tool. Measure before and after any change to evaluation, rendering, the canvas, the timeline or the panels:

```bash
cd Packages/MotionKit && TWINE_BENCH=1 swift test -c release --filter PerformanceTests
```

That prints per-frame timings for a 200-layer, 990-action scene (`stressProject` in `Tests/MotionRenderingTests/PerformanceTests.swift`; `TWINE_BENCH_OUT=path` writes it as a document to open in the app). In September 2026, release build: evaluate 1.06 ms (28 September, after walking only a layer's own channels; 1.2 before), still layout 0.4 ms, layer tree update 0.34 ms (0.30 before blend modes and path shadows), a 1080p offscreen frame 11.4 ms (14.6 before); in the app, playback 60 fps, a canvas drag step 6 to 8 ms, a timeline bar drag step 9 ms, a scrub step 4 ms, selecting a layer about 27 ms (SwiftUI building the inspector). Profile the running test copy with `sample <pid> 5` and read the main thread's call tree.

For very large projects (a Figma import of dozens of screens) there is a second scene, `largeProject` (5,050 layers in 50 frames, 550 actions on the first hundred or so layers), and an editing one (`LargeProjectTimings` in `Tests/MotionEditingTests`):

```bash
cd Packages/MotionKit && TWINE_BENCH=1 TWINE_BENCH_LARGE=1 swift test -c release --filter largeStages
cd Packages/MotionKit && TWINE_BENCH=1 swift test -c release --filter LargeProjectTimings
```

On 1 October 2026, release build: evaluate 1.8 ms a frame with an `EvaluationCache` (8.6 without), a design drag step's evaluation 1.5 ms, the layer tree update 2.1 ms (1.8 when nothing changed; it was 6.4), applying an edit 1.7 ms (4.3), finding a layer's place 0.15 ms (0.9), a 320-pixel thumbnail 170 ms, encoding the 13 MB file 120 ms. In the app (`Tools/SelfTest`, the large scene saved as `Large.twine` with its texts fitted, `perfdragat 700 450 40` and friends): playback 60 fps (25 before), a scrub step 8.6 ms (105), a press on the canvas 13 to 17 ms (5.8 seconds before), a drag step 22 to 27 ms (48 to 52), selecting about 30 to 40 ms (mostly the inspector, as in small projects), a save after the first 148 ms (307 to 446).

What keeps it fast, and must stay so: the canvas, the inspector's scene, the export preview and every export keep an `EvaluationCache` (pass it to `evaluate`/`evaluateDesign`): a layer no action reaches is resolved again only when it changed, and a still group (no action or mask anywhere in it) whose value is the same, children and all, hands back its whole run of resolved layers at once (unchanged lists compare at once, as they share storage); entries are classes, since copying a layer out of a dictionary cost more than resolving it. `CoreAnimationRenderer.render` reads layers by index and, while every layer is where it was under the same parent (`drawn`), skips rebuilding the tree; `Node.update` compares without wrapping the layer in an optional, which copied it. Walks of the layer tree use `Project.forEachLayer`, `location(of:)`, `parents`, `lockedLayers` and `isLocked(_:)`, which read layers in place: `allLayers` copies all of them (a millisecond at 5,000), and anything asking it, or `ancestors(of:)`, once per layer was seconds (pressing on the canvas gathered snap targets that way). `ResolvedScene`'s world transforms and `parentID(of:)` read in place too. Snapping keeps only candidates within reach and finds each gap's neighbour by halving. `TextLayout` keeps 4,096 layouts a generation (at 512, a project with 630 texts laid most out again every edit). A save leaves the thumbnail alone once drawing it took over 50 ms, and `ProjectDocument.close` draws it into the package (the home screen keys its cache on the thumbnail's date too). `ActionTracks.state` walks only the channels a layer has actions on, and copies no lists when all actions count (it used to walk all two dozen and filter each, which took evaluate from 1.06 ms to 1.25); `TextLayout` keeps the installed font families (`installed`, cleared with its caches on `kCTFontManagerRegisteredFontsChangedNotification`): asking Core Text for them took about 100 ms on the user's Mac and was done for every new style, 1.6 s of opening a project with 16 styles; `TextLayout` caches fonts and laid-out lines behind a `Mutex` (text is the dearest thing in a frame); `ResolvedScene` looks layers up through an index built once in `init`, so its lists are `let`; `CoreAnimationRenderer`'s `Node` skips a layer whose `ResolvedLayer` is unchanged (pictures and video always refresh); the timeline sorts small keys, not whole actions; ids compare by bytes (`UUID.precedes`), never by `uuidString`. Never do per-row or per-layer work that scans the whole project (the layers panel once checked every layer for masks in every row; `evaluate` once looked up every layer's mask by searching the project, 45.7 ms a frame for 1,000 layers with one mask, now 1.8 ms: masks are noted during the walk and `WorldTransforms` indexes layers and parents once). `TextLayout`'s layout cache keeps two generations of 512 (`Generations`), carrying what is found in the older into the newer, so a Counter's new entry every frame never flushes texts in use. The renderer keeps a shape's area (`Node.area(of:)`) and an inner shadow's last inputs, so shapes with pictures, updated every frame, do not redo boolean operations. After changing a stored property of a struct in MotionKit, run `swift package clean` (and delete `build/DerivedData` for the app): an incremental build can keep the old layout and crash in ways that look like real bugs.

## Cursors

`Twine/Components/Cursors.swift` loads the designer's 32 by 32 SVGs from `Twine/Resources/Cursors` (copied from the supplied set in `~/Desktop/26-09/Cursor`; the brush one is unused) as `NSCursor`s, falling back to system cursors. `Cursors.arrow` replaces the system arrow everywhere: `Cursors.useAppArrowEverywhere()` (called first thing at launch) swaps `+[NSCursor arrowCursor]` for it with `method_exchangeImplementations`, because SwiftUI's hosting views set the arrow on every mouse move and cursor rects cannot overrule them. `CursorArea` and the timeline's base cursor rects use it too. Write `Cursors.arrow`, not `NSCursor.arrow`, so the intent reads plainly. SwiftUI puts its arrow back over cursor rects as the pointer moves, so AppKit views set their pointers on `mouseMoved` and `cursorUpdate` too (the ruler: `TimelineRulerView.cursor(at:)`, with the whole ruler taking the held pointer while its pill or the scene end is dragged), and SwiftUI views use `.pointerStyle(.image(...))` (the timeline's top edge). The pen has four (`pen`, `penAdd` over a segment, `penMove` over a point, `penConnect` over an end it can join), set on `mouseMoved` by `pathMouseMoved`, hot spot at the nib. `Cursors.moveAll` (the designer's all-direction arrows, `cursor-move-all.svg`, 5 October 2026) shows over a gradient's ends, third handle, stops and line and while they drag (`gradientMouseMoved`, `gradientPart(at:in:)`). `Cursors.resize(toward:)` and `.rotate(toward:)` pick by the handle's or corner's direction on screen, so turned layers get the right arrows. Hover is shared: `EditorModel.hoveredLayer` is set by the canvas (`setHover`, which only clears its own) and by layers panel rows, and both draw it: the canvas in the selection's one-point accent line, following the layer's own shape as Figma does (`CanvasNSView.hoverOutline`: a shape's or frame's path, the box for text, groups and tilted layers; the user's choice on 29 September 2026, replacing a white line on a dark edge round the box), with no wash inside, nothing on a selected layer (the user wants only the selection box there), the row as its full hover state (`LayerRow.lit`, switches included).

## Icons

SVGs in `Icons/`, 24x24, stroked, `M L H V C Z` only. A path's `opacity` attribute is kept (`Icon.opacities`, generated only for icons that have one; `IconView` draws each strength as its own `IconShape(opacity:)`), as the fill-linear icon's fading dots need; stroke widths are not, every line being drawn at `Theme.iconStroke`. The four `fill-...` icons (Solid, Linear, Radial, Image; the designer's, from `~/Desktop/29-09/Fill Icons`, 29 September 2026) label the fill kind segments through `Icon.fillKind`. Since 28 September 2026 every icon the app shows is the designer's (supplied in `~/Desktop/28-09`, copied in under the existing names; the music note's filled stem and flag were traced to a centre line, since icons are stroked). The designer's icons are Hugeicons (stroke rounded, the free set), most unchanged; every icon that was a stand-in of ours was replaced with a Hugeicons one on 19 October 2026 (the user's request), so none of ours is left. Take any new icon from Hugeicons too: the free set is the npm package `@hugeicons/core-free-icons` (MIT), each icon a `dist/esm/NAMEIcon.js` list of SVG elements, which must be written as absolute `M L C Z` paths (arcs cut into cubics, circles and rects as paths) for `svg_to_swift.py`; the Hugeicons MCP server finds names but gives only font glyphs. The four `corner...` icons label the per-corner radius fields. `Layers/template-layer.svg` (the designer's, Figma node 215:3892 of `RRnath7INm7WH7CGLOfLdH`, 19 October 2026) marks template frames in the layers panel (`Layer.icon`); `Actions/template.svg` (Hugeicons' CarouselHorizontal) is the action and tile icon. The app draws every icon's line at `Theme.iconStroke` (1.92 on the grid, heavier than the artwork's 1.5; the user's choice), scaling with the icon, so a 20 pt icon has a 1.6 pt line. Regenerate after editing:

```bash
python3 Tools/svg_to_swift.py --icons Icons --out Packages/MotionKit/Sources/Theme/Icons.swift
```

The app icon is the designer's artwork, `Artwork/AppIcon.png` (a full-bleed square), set into the macOS icon grid (an 824 pt rounded square in a 1024 pt canvas, with a soft shadow) by `swift Tools/make-app-icon.swift Artwork/AppIcon.png Twine/Resources/AppIcon.icns`.
